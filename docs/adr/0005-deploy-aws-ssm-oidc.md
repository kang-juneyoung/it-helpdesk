# 0005. AWS 배포: GitHub Actions + OIDC + SSM

## 상황

전산 담당 한두 명이 운영하는 사내 시스템이다. 배포는 사람이 서버에 SSH로 들어가 손으로 하는 경우가 많고,
그 과정에서 순서를 빠뜨리거나, 서버 접속 키와 AWS 액세스 키가 여러 PC에 흩어진다.

## 결정

- **테스트를 통과한 커밋만 배포한다.** CI가 main에서 성공해야 Deploy가 시작되고, 통과한 바로 그 커밋 SHA를 배포한다.
- **이미지 태그 = 커밋 SHA.** 서버에 어떤 코드가 올라가 있는지 항상 알 수 있고, 롤백은 이전 SHA로 되돌리기만 하면 된다.
- **AWS 인증은 OIDC.** GitHub에 장기 액세스 키를 저장하지 않는다. 역할은 이 저장소의 production 환경에서만 맡을 수 있다.
- **서버 접속은 SSM.** 22번 포트를 열지 않고 SSH 키도 만들지 않는다. 배포 역할은 `App=it-helpdesk` 태그가 붙은 인스턴스에 셸 명령을 보내는 권한만 있다.
- **헬스체크 후 자동 롤백.** 로그인 화면이 정상으로 뜨지 않거나 PHP 오류 문구가 보이면 직전 버전으로 되돌리고 배포를 실패로 표시한다.
- **비밀번호는 서버에만.** DB 비밀번호는 EC2 처음 만들 때 무작위로 생성해 서버의 `.env`에만 둔다.

## 고려한 다른 방법

- SSH로 접속해 배포: 가장 단순하지만 22번 포트 개방과 SSH 키 관리가 필요하다.
- ECS/Fargate: 무중단 배포·오토스케일링은 좋지만, 이 규모에서는 비용과 설정이 과하다.
- CodeDeploy: 기능은 충분하지만 에이전트·설정 파일이 늘어난다. SSM 명령 하나로 같은 목적을 이룬다.

## 한계

- 인스턴스 한 대라 교체하는 몇 초 동안 접속이 끊긴다(무중단 아님).
- DB 스키마 변경(마이그레이션) 롤백은 다루지 않는다. 앱 코드만 되돌린다.
- DB 백업은 이 배포 범위 밖이다(운영이라면 EBS 스냅샷 일정 또는 mysqldump + S3).
